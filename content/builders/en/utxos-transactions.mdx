M-Pesa keeps one balance per account. Bitcoin doesn't. Instead, it keeps a set of separate coins, each locked to an owner. Your "balance" is just the sum of the coins your keys can unlock.

## Step 1: The UTXO model

Each coin is an **unspent transaction output**, a <Term id="utxo" />. A <Term id="transaction" />:

1. **Consumes** one or more UTXOs as inputs (they are now spent, gone forever).
2. **Creates** new outputs, each with an amount and a locking script.
3. Proves, with a signature, that the spender may unlock each input.

Think of notes in a purse. To pay 300 shillings with a 500 note, you hand over the whole note and get 200 back as change. Bitcoin does the same: a payment usually has one output to the receiver and one **change** output back to you.

The <Term id="fee" /> is never written down. It is whatever is left over:

```text
fee = sum(inputs) - sum(outputs)
```

**Done when:** you can compute the fee for inputs of 0.6 and 0.5 BTC and outputs of 0.3 and 0.79 BTC. (Answer: 0.01 BTC.)

## Step 2: Look at your coins

Start your lab from the previous lesson, then:

```bash
bitcoin-cli -regtest -rpcwallet=alice listunspent
```

Each entry is one UTXO with a `txid`, a `vout` (output index) and an `amount`.

## Step 3: Pay Bob and decode it

```bash
bitcoin-cli -regtest createwallet "bob"
BOB=$(bitcoin-cli -regtest -rpcwallet=bob getnewaddress)
TXID=$(bitcoin-cli -regtest -rpcwallet=alice sendtoaddress "$BOB" 1.5)
bitcoin-cli -regtest getmempoolentry "$TXID"
RAW=$(bitcoin-cli -regtest -rpcwallet=alice gettransaction "$TXID" | jq -r .hex)
bitcoin-cli -regtest decoderawtransaction "$RAW"
```

In the decoded JSON find `vin` (the inputs) and `vout` (the outputs). One output pays Bob 1.5 BTC; the other is Alice's change. The transaction is waiting in the <Term id="mempool" />.

<Callout type="tip" title="No jq?">
Run `gettransaction` and copy the `hex` field by hand, or install `jq`; it is useful throughout this path.
</Callout>

## Step 4: Confirm it

```bash
bitcoin-cli -regtest generatetoaddress 1 "$(bitcoin-cli -regtest -rpcwallet=alice getnewaddress)"
bitcoin-cli -regtest -rpcwallet=bob getbalance
```

**Expected:** Bob's balance is `1.50000000`. The transaction now has one <Term id="confirmation" />.

**Done when:** you can point to the change output in the decoded transaction and compute its fee.

## Transaction identity and SegWit

A payment's intention and a transaction's byte-level identity are different. A transaction ID is derived from serialization. Historically, some changes to signature encoding could change a transaction ID without changing the intended payment. A later transaction spending an output identifies its parent by transaction ID, so an unexpected change can break that dependency.

SegWit separates witness data from the serialization used for the transaction ID. The witness transaction ID also commits to witness data. This addresses important unwanted malleability cases and supports protocols that depend on transactions before confirmation. It does not mean every possible transaction change preserves an ID or that a signature alone guarantees settlement.

In your regtest decoded output, compare the transaction ID, witness-related hash where reported, inputs, outputs and virtual size. Read BIP 141's definitions before explaining which data each identifier commits to. For the discussion, identify an assumption under which a parent ID remains stable and one modification that changes the payment itself. No additional mainnet transaction is needed.
