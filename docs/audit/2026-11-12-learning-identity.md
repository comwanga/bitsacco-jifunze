# Built-in learning identity: security assessment

## Decision before completing implementation

Keep the existing NIP-98 challenge verifier, PostgreSQL accounts/progress, HttpOnly sessions, recovery scope and identity replacement transaction. Generate a separate secp256k1 learning key with `nostr-tools/pure` in the browser, commit it to IndexedDB before authentication, and submit only signed, purpose-bound proofs. A public key or browser marker is never authentication.

IndexedDB is origin-scoped storage, **not a secure enclave**. The key is readable by same-origin JavaScript and is not encrypted at rest by this application. Encrypting it with an automatically available key stored beside it would not prevent an active same-origin attacker from signing or recovering the plaintext. A password would add an unlock/backup burden; WebAuthn/passkeys would require another authentication model and backend work. Neither is part of this smallest implementation. Web Crypto does not supply the Nostr Schnorr signing operation used here. OS disk encryption, screen lock and browser-profile security remain device responsibilities.

- Browser clearing, eviction, private browsing, profile loss and a lost phone can destroy the key. Request persistent storage as a best effort only. Require acknowledgment of recovery-code backup during onboarding; recommend private storage separate from the phone. Codes recover the account by authorizing identity replacement, not by reconstructing its original key.
- An unlocked/shared browser can use the identity. Offer explicit identity removal at device sign-out, checked by default. Ordinary logout ends the cookie session but keeping the key permits deliberate sign-in again. Signing reads storage afresh; no long-lived secret closure remains after removal. Removing an IndexedDB record is logical browser deletion, not guaranteed forensic erasure. Device removal cannot remotely wipe another browser or defeat malware.
- XSS, malicious same-origin releases, hostile extensions and compromised devices can steal or use this key and act through an authenticated session. Existing script hashes/CSP, output escaping, no untrusted script insertion, dependency review and no third-party scripts are defenses, not guarantees. The advanced sign-in page still permits relay WebSockets; do not claim CSP prevents all exfiltration. Scope the built-in signing function to this origin's three authentication proof routes. Never publish events or send learner progress to relays.
- Keep secrets out of URLs, Web Storage, exports, UI, API payloads and logs; clear transient key buffers after use. Validate stored data and fail closed on corruption/storage failure. Recovery codes stay in component memory until deliberate copy/download, and are cleared when the page is hidden.
- A stolen recovery code can recover an account; a stolen signing key can authenticate and change account security. Recovery cannot undo an attacker's changes/deletion or assure ownership if both recovery and signing authority are compromised. Warn plainly about these limits. Never use this identity for Bitcoin funds or as a primary Nostr identity.
- Match the actual stored public identity against the server's authenticated identity before selecting built-in reauthentication. Recheck session/account scope and send the existing account expectation on sensitive mutations. Preserve progress ownership/merge consent. Device sign-in refuses to replace a different existing browser account; a matching full session continues directly.
- Multiple sessions can coexist. Recovery-code redemption and identity replacement revoke earlier sessions under existing backend rules. Replacing a key does not export it to another device. One browser profile keeps one learning identity; shared-device users should remove theirs at sign-out and retain recovery codes.
- Staging stays tester-only: a randomly generated key is denied until its public key is explicitly allowlisted by an operator. The advanced section can show that **public** key for tester enrollment. Do not auto-enroll, weaken replacement checks, change allowlist configuration, enable public accounts, deploy, or touch production.

Sources checked 2026-11-12: [OWASP HTML5 Security](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html) (IndexedDB is exposed to XSS; treat storage as untrusted), [MDN storage eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) (persistence is a request; explicit clearing can still remove data), [MDN signing algorithms](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/sign) (Web Crypto signing algorithms do not provide Nostr's secp256k1 Schnorr operation).

## Validation

Local checks use the real browser application, API and fresh throwaway PostgreSQL databases in the existing local test container. An older test database contained stale failure-injection triggers and an unfinished transaction from earlier work; it was left untouched. API tests use a separate new database because they intentionally reset their own schema. No production/staging connection or configuration was used.

| Requested evidence | Verification |
| --- | --- |
| New learner saves without technical steps | Both languages: the default button creates a stored device identity, sends a valid signed proof, shows ten codes, requires backup acknowledgment and adds pre-existing progress only after consent. No external signer or relay is used. |
| Returning learner avoids onboarding | A matching full session continues without a new proof. With cookies removed, the retained key reopens the same account without welcome codes. |
| Recovery after loss | Tests cover a fresh browser and explicit deletion of IndexedDB, local/session storage and cookies. A recovery code attaches device access to the same account and restores server progress; old sessions and old code sets cease working. |
| Shared-device isolation | Default sign-out removes the key; an intentional retain choice is tested separately. A second generated identity receives its own account, never uploads or replaces another account's retained copy, and receives no first-account server progress. Cross-tab sign-in refuses a newly appeared session. A stale sign-out page is bound to the account it displayed and cannot end a different learner's session or erase the earlier device key; external-account sign-out does not remove an unrelated retained identity. |
| Failures preserve work | Storage denied/corrupt key fails before a proof; concurrent creation converges on one key; a failed challenge retries with that key. Existing sync tests cover offline work, reconnection, expired sessions and explicit replacement; account controls cover lost responses and retention of unsynchronized work. |
| Security/browser/performance checks | Final command results recorded below. Existing CSP, build limits, rate limits, account expectations and tester allowlist remain enforced. |

An account owner marker prevents server-side mixing; it is not encryption of locally retained progress. A learner who deliberately retains local work leaves it readable to people using that browser/profile. Unsynchronized work remains on the device to avoid data loss and the UI warns about it. A shared/unlocked profile, deliberately retained signing identity, malicious extension, same-origin compromise or compromised device cannot provide confidentiality between people. Use the default sign-out removal on shared devices; export unsent work privately before clearing site data. Do not interpret the isolation tests as protection against these threats.

### Remaining acceptance and operational limits

Kiswahili wording needs owner/native-language review. Real phones, Firefox/Safari authenticated flows and real external signer applications have not been certified by these local Chromium/simulated-signer checks. Browser-storage loss of **unsynchronized** work cannot be recovered from PostgreSQL; keep a private progress export when offline. Recovery codes and device-key deletion do not defeat an unlocked/compromised profile, XSS, malware, profile backups or forensic recovery.

Staging configuration, tester enrollment and production were not changed. Generated staging identities still require explicit operator allowlisting of the public key. The working tree is on `feat/learning-identity`; no commit, push or deployment was made. The pre-existing `debug.log` was left alone.
