## Security findings

| Area | Evidence / finding |
| --- | --- |
| Generated signing identity | `lib/nostr/device-identity.ts` uses the existing pinned `nostr-tools/pure` secure key generator; commits a valid key to IndexedDB before authentication; concurrent creation uses `add`, not overwrite. Secret buffers read/generated by this module are cleared after use. No export/private-key input is introduced. |
| Storage boundary | IndexedDB is origin-scoped, unencrypted application storage. Same-origin scripts, malicious releases/extensions and compromised or unlocked profiles can use/read the key. Persistence is best effort; browser clearing, eviction or profile loss can destroy it. Record removal is not forensic erasure. CSP/escaping/dependency review reduce exposure and are not a secure enclave. This matches [OWASP's browser-storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html). |
| Proof and session authority | `nostr-proof.ts`, `api/src/nostr.ts`, `nostr-routes.ts` and `http.ts`: signed purpose/URL/method/body-bound NIP-98 proofs, browser-bound single-use challenges and server signature verification remain required. A public key, account hint or expected-account header is not authentication. Secure HttpOnly `__Host-` cookies remain the session credential; Strict without GitHub, Lax when its redirect flow is configured. |
| Sensitive account operations | `accounts.ts` checks live session/scope and recent reauthentication inside transactions. Replacement preserves the account/progress while rotating sessions and recovery codes; occupied identities are refused. Deletion requires a fresh full-session proof and explicit confirmation, and cascades account-owned data. Restricted recovery sessions cannot read/write progress. |
| Shared profile / account switching | Known-account requests carry the existing server-checked expectation. Sign-out is bound to the account loaded by its page and conditionally removes the expected device identity. Local ownership prevents uploading/merging a different account's copy; it does not encrypt that copy. Deliberate retention, unsynchronized work, a retained key or an unlocked profile remain readable/usable locally. Separate browser profiles or the default removal choices are necessary for shared-device privacy. |
| Progress integrity | `lib/progress/sync.ts` and API progress merge rules retain concurrent/offline work, require explicit consent for unclaimed work and do not automatically replace foreign work. Confirmed coverage of the latest canonical device copy is required before removal. Lost responses remain uncertain rather than successful; unsupported/future timestamps are retained locally rather than invented or discarded. |
| Recovery and export | Recovery codes are HMAC-hashed server-side; plaintext appears once in memory and only deliberate copy/download writes it elsewhere. Initial backup acknowledgment is required. Codes restore account access through key replacement, not the original key or unsynchronized lost-device work. They cannot undo deletion or attacker changes. Progress JSON contains progress fields, not signing keys, session cookies, recovery codes or account ownership markers. |
| Feedback | `lib/feedback.ts` accepts only a configured plain mailbox and static public curriculum context; it rejects query/fragment/account/external context paths and strips title controls. `FeedbackLink.tsx` is server-rendered and reads no browser state. The draft has only recipient, subject and body; no account/progress/credential data or mail-sending endpoint. The recipient is public. The user controls their email client, sender/signature and any additional content they choose to send. |
| Logging and CSP | No new logging or script/network permissions. Existing per-page CSP hashes, no unsafe script evaluation, no third-party feedback SDK, account/API no-store and service-worker exclusions remain. API request logs contain route/status/duration, not request bodies, cookies or proofs. NGINX error logs can include request lines/client addresses; provider edge logs and their retention still need operational acceptance. |
| Demonstrated corrections | Feedback browser testing found its native copy disclosure was not exposed as a button to accessibility/test tooling; an explicit button role fixed keyboard/screen-reader discoverability without client JS. The layout regression's staging-only sign-in expectation was updated from external-signer help to the approved Save Progress action, with a negative assertion that the external signer is absent by default. No demonstrated auth/backend defect requiring a new correction was found in this pass; existing controls were preserved. |

Browser-storage and recovery limitations remain visible to learners. This identity is exclusively for learning progress, never a wallet, Bitcoin funds or a primary external Nostr identity. Local automated tests do not certify physical phones, authenticated Firefox/Safari flows or real external signer applications.

## Data inventory and retention actually implemented

Evidence: `api/migrations/0001_accounts.sql`, `0002_progress.sql`; `accounts.ts`, `sessions.ts`, `challenges.ts`, `recovery.ts`, `main.ts`; `lib/progress/model.ts`, storage/sync; NGINX logging configuration and account operations documentation.

| Information / purpose | Storage and access | Deletion / retention |
| --- | --- | --- |
| Dedicated private learning key; proves control | This origin's IndexedDB only; readable by the browser/profile and same-origin scripts. No application at-rest encryption. The server receives public signed proofs only. | No automatic TTL. Default device sign-out removal or explicit browser site-data clearing; not remote wiping, backup erasure or forensic erasure. Account deletion alone does not remove every local copy/key. |
| Device progress; anonymous/offline continuity | Browser storage: lesson identifiers, completion/discussion-confirmation timestamps, best quiz score/count/time and lab-pass IDs. No discussion prose, individual quiz answers, wallet balance, seed phrase or group-membership field is collected. Anyone using that profile can read retained data. | No automatic TTL. Explicit local removal only when safe; unsent/foreign work is retained to avoid loss. Browser clearing/loss can destroy it. User-chosen plain JSON exports remain wherever saved/shared. |
| Account UUID, preferred language, creation/recovery-issue times; stable progress ownership | Private PostgreSQL account row. API uses session-derived ownership. Authorized infrastructure/database administrators and processors can access server data; application users receive their own account data. | Stored until explicit account deletion; no inactive-account expiry policy is implemented. A time-bound retention policy still needs an owner/legal decision. These pseudonymous identifiers can be personal data; they are not asserted anonymous. |
| Public sign-in identity; binds account ownership | PostgreSQL provider/public Nostr key; retained GitHub compatibility adds GitHub numeric ID, handle and avatar URL. No generated secret key is stored server-side. | Key replacement removes/replaces the earlier provider identity. Account deletion cascades identities. Existing allowlist membership/operational config is separate and must be reviewed when removing a tester. |
| Server progress; cross-browser restore/sync | PostgreSQL `lesson_progress`, account-owned versions of the device fields and update timestamps. No raw discussion or quiz-answer text. Hosting region/encryption/backups are operational facts not verified by this local review. | Account deletion cascades progress. Otherwise retained with the account; no independent progress TTL. Browser/export copies and provider backups are not automatically erased by that SQL cascade. |
| Sessions; authenticated requests | Cookie contains a random token; database keeps its SHA-256 hash, account/scope and times. `user_agent` exists as a nullable schema column but current `createSession` does not populate it. | Full sessions: 14-day idle / 30-day absolute expiry; recovery: 15 minutes. Boot/daily purge deletes expired/idle sessions and revocations older than a day, so physical removal may lag expiry. Revocation invalidates access before purge. |
| Authentication challenges / PKCE; replay/CSRF binding | PostgreSQL hashed nonce/state and browser binding; GitHub PKCE verifier is temporarily server-side. Known-account challenges hold session/account bindings and a safe relative return path. | Nostr 5 minutes, remote 2 minutes, GitHub 10 minutes; expired rows removed by boot/daily purge. Expiry is not a promise of immediate physical deletion during outages. |
| Recovery codes; restore account access | PostgreSQL HMAC hashes, pepper version/set IDs and creation/use times; server pepper in deployment secrets. Learner's deliberately saved plaintext copy is outside server control. | One use per code. No time-based code expiry. Regeneration/replacement deletes the prior set; account deletion cascades the set. Losing the device/key and all codes means no supported account recovery by public key alone. |
| Security events; account safety and recovery notices | PostgreSQL event/time/provider/outcome or counts, linked to an account while it exists. Current call sites do not store secret keys/codes/session values or free-form learner messages. | Boot/daily purge after 90 days. Account deletion sets the foreign key to null and records a deletion without account identity; disassociated event rows remain until purge. This is not a claim that timing correlation or backups become irreversibly anonymous. |
| HTTP/platform logs; operation and abuse limits | API route/status/duration; hourly aggregated recovery outcomes. NGINX access logs use path only and truncated IPs; NGINX error lines/platform edge logs can contain additional request/address information. Operators/provider access depends on their actual configured roles. Rate buckets are in memory. | Application design calls for 14 days; Compose only bounds file size. Current Railway/edge age retention and backup policy are **not verified**. Confirm actual enforcement before public accounts; do not present a policy statement as an implemented retention guarantee. |
| Feedback email; learner-requested support | Nothing is submitted to a Jifunze backend. Email goes through the learner's chosen mail application/provider to the configured recipient's mailbox. Sender address, signature and voluntarily written content may be included by that software. Recipient/mail-provider administrators may access received mail. | Recipient mailbox retention, provider location and deletion handling are not set by this website and need an owner policy. Do not ask learners to send recovery codes/private keys. Provide a verified support/rights-request process rather than treating an email/public key as account ownership proof. |

Learners can view/export device progress and, while authenticated, restore the server copy. The account safety flow deletes account-owned server records after fresh proof and explicit confirmation. No email address is required for a built-in learning account. Anonymous learning does not create an account or upload progress, but normal hosting requests/logs still exist.

If a device is lost, a saved recovery code permits attaching a new learning identity to the same account and restoring **server-saved** progress; earlier sessions/codes rotate. If only the cookie expires but the stored key remains, ordinary sign-in resumes without onboarding. If every ownership credential is lost, there is no public-key-only recovery or private-key reconstruction. Unsynchronized lost-device work and local exports are outside PostgreSQL recovery.

## Qualified external privacy/legal review required

Given the Kenyan audience, obtain qualified advice on the Data Protection Act, 2019 and the current ODPC regulations/guidance, including controller/processor roles, registration or applicable exemptions, lawful basis, learner notice/contact, access/correction/erasure/portability procedures, proportionate identity verification, and retention schedules. Confirm processor agreements, actual hosting/backup/mail locations and cross-border safeguards; do not infer database location from an edge header. Assess DPIA applicability, incident/breach-response duties, and children's-data safeguards if minors are served. Consider other jurisdictions if learners there are actively targeted. No compliance certification or financial-services classification is inferred from educational SACCO/chama content. [ODPC regulatory framework](https://www.odpc.go.ke/data-protection-laws-kenya/index.html), [official Act](https://www.odpc.go.ke/wp-content/uploads/2024/02/TheDataProtectionAct__No24of2019.pdf), [General Regulations](https://www.odpc.go.ke/wp-content/uploads/2024/03/THE-DATA-PROTECTION-GENERAL-REGULATIONS-2021-1.pdf), [Registration Regulations](https://www.odpc.go.ke/wp-content/uploads/2024/03/THE-DATA-PROTECTION-REGISTRATION-OF-DATA-CONTROLLERS-AND-DATA-PROCESSORS-REGULATIONS-2021.pdf).

Unverified operational retention, backup/restore, access roles, data location, privacy notice/rights handling and live staging acceptance are release gates, not newly invented code vulnerabilities. No legal compliance or independent specialist approval is claimed.
