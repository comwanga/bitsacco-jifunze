## Architecture and active functionality

Next.js 16 static export, React 19, TypeScript, Zod, build-time MDX and CSS/Tailwind. `lib/content/{schemas,load,catalog,tree,validate}.ts` share roadmap metadata, bilingual files and quizzes. MDX is executable **trusted repository input**, compiled during build; it is not an upload format or a safe untrusted-content sandbox. Contributions require code review, including MDX.

Three active learning paths have 33 lessons / 66 language files and 33 bilingual quizzes: Savers 8, Bitcoin Builders 8, Lightning Builders 17. The latter adapts *Mastering the Lightning Network* and has 20 registered lab exercises. Quizzes can complete reading lessons; labs have separate completion requirements. Prerequisites are reading guidance, not access restrictions. Learners may inspect any lesson.

`lib/progress` uses language-independent `roadmap/slug` keys, version-1 browser storage and validated JSON import/export. No public server progress synchronization or account is needed. Language switching preserves the lesson route. Browser privacy/quota restrictions are surfaced; clearing browser data can erase progress. Exported files remain the portable backup.

Two active simulations model UTXOs and settled Lightning channel balances. They load their interactive modules on request; static explanations and limitations work without JavaScript. They use fictional sats, never wallet connections. The separate Docker Lightning lab runs learner-owned regtest infrastructure with paired bridge access, not a hosted production financial service. Its arbitrary learner-code execution is deliberately not an egress-isolated security sandbox (`lab/README.md`).

Public production is anonymous static NGINX, with `/api` rejected by the Railway entrypoint's static configuration. GitHub OAuth, PostgreSQL sessions, recovery and Nostr code remain for local compatibility/isolated acceptance. The account/community design is partly historical; community publishing, cross-provider identity lifecycle and remote progress synchronization must not be represented as active learner features.

## Security and reliability assessment

Inspection covered `api/src/{http,config,sessions,challenges,github,github-routes,nostr,nostr-routes,recovery,accounts,ratelimit}.ts`, build CSP, service worker, Docker entrypoint/configuration, CI and deployment guides. This is source review and automated local validation, not a penetration-test certification.

- HTTP mutation routes check exact origin and a custom header, bound bodies, use Zod input schemas, scoped sessions and parameterized SQL. Sessions use random opaque tokens with hashed database storage, Secure/HttpOnly/SameSite cookies, expiry and revocation. Recovery is transactional and rate limited; restricted sessions cannot use ordinary full-session routes.
- OAuth uses bound single-use challenges, state and PKCE; provider tokens stay within the exchange call. Nostr verifies canonical event encoding, BIP340 signatures, timestamp, exact URL/method/body digest and browser-bound single-use challenges. Real-provider/signer acceptance remains separate from fixtures.
- API trust of a private peer's `X-Real-IP` requires isolated API ingress and NGINX overwriting the header. It is not appropriate to publish the API directly. In-memory rate limits reset on restart and do not coordinate replicas. Existing authenticated-production gate remains in force.
- Per-page CSP hashes avoid script `unsafe-inline`; only lab pages allow the lab bridge endpoints. Style inline allowance is an existing rendering choice. NGINX adds frame denial, MIME protection, no-referrer and restricted browser capabilities. These files do not prove today's deployed headers.
- Service worker excludes API, private account/community navigation and book PDFs. Opened lessons are cached, not the whole course. Offline availability depends on previous successful loading and browser cache retention. Old static chunks are bounded at activation.
- No secret values were needed or printed. Ignore/build boundaries exclude local API environment files. A complete historical secret scan was not performed; absence of secrets is not certified.
- CI has separate frontend, PostgreSQL/account and Docker lab jobs, read-only repository permissions and artifact retention on failures. Build gates check CSP, internal routes, PDFs and performance. Browser suites cover mobile emulation, keyboard/tables, Axe, offline, progress, quizzes and simulations. CI configuration is not evidence of a new successful CI run.
- Railway, DNS, TLS and account-provider behavior were not changed or re-certified. `docs/deployment/production.md` records acceptance at `39fa78a` on 6 November; its monitoring and resource observations are historical.

## Educational assessment and architecture decision

Preserve all eight introductory slugs, their order, progress keys, quizzes and builder routes. Append three optional modules **inside the Savers roadmap**, rather than inventing a parallel curriculum/progress model or forcing savers into developer labs. Sections already carry prerequisites and completion summaries and feed list, tree, catalogue, sitemap and reader navigation.

Specializations: individual financial resilience/sovereignty; community savings/governance; cooperative institutions/responsibility. Each progresses from foundations through intermediate practice to advanced failure planning. Optional module descriptions and navigation must explain that learners can choose one; introductory completion remains a meaningful milestone. Prerequisites guide readiness without locking content or inventing qualifications.

Before this expansion, individual coverage omits cash-flow timing, nominal/real calculations, reserve access, concentration and inheritance. Community coverage lacks ROSCA/accumulating distinctions, contribution reconciliation, membership disputes and collusion/recovery. Cooperative coverage lacks member ownership, loan impairment, maturity mismatch, audit, member protection and legal permission boundaries. Existing scams/wallet/Lightning introductions provide useful prerequisites and should be reused.

Primary-source research is documented with the lessons and in the curriculum record. Cases and calculation assumptions are explicitly fictional. No allocation recommendation, return forecast, legal authorization or claim that Bitcoin eliminates credit/liquidity/governance risk is appropriate.
